CHAPTER 3 Iceberg ♥ Pinot Same shape, so no copy

One Parquet file, one Pinot segment

  • Name = hash of the file path
  • Paths never change content
  • Segment holds no data
  • Its forward index is the Parquet file
  • Segment name = murmur3_128(file path)
  • Safe because Iceberg never rewrites a committed file
  • Segment = metadata + indexes + pointer to the Parquet file, on the S3 tier

From catalog to query

  1. Controller reads the snapshot
  2. New file: footer only, tiny segment
  3. Server builds indexes, stores them on S3
  4. Snapshot published
  5. Broker pins it per query
  • Controller reads only footers
  • Server builds the indexes once and uploads them (no data) to the S3 tier
  • Broker pins one snapshot
  • Cost: one read per indexed column; 270 GB of indexes on 770 GB of data

Same Parquet, same hardware

StarTree benchmark: 12.2 B rows, 770 GB Parquet on S3, 4 × r6gd.4xlarge for every engine. Trino 476 (Iceberg connector), ClickHouse 26.2 (icebergS3Cluster). Indexes add 270 GB.

  • Our benchmark: same Parquet, same 4 × r6gd.4xlarge for every engine
  • Cold, StarTree vs Trino: 21x, 9.5x, 8.5x, 3.9x faster
  • Pinned is not a cache: indexes always local, data still from S3
  • Network in: 4.2 GB vs ~20 GB
  • Method: 5–10 warm-up queries, 100 sequential runs

Filtering with an index

  • Same picture as tiered storage: only the file changes
  • Indexes give exact doc IDs; the page index gives byte ranges
  • Pinot's page index: ~32–36 B per page, built once
  • A Parquet page is compressed as a unit: read it whole (~170 KB each)
  • 3 ranged GETs: 0.5 MB of 512 MB; tiered segment ~24 KB (1,000-doc chunks)
  • Illustrative numbers

Inverted indexes don't help aggregations

  • Aggregations read ~80 M rows each
  • Pinning: 515 → 483 ms, 645 → 615 ms
  • Only 30 and 7 QPS, server CPU bound

Star-tree index

  • Same file, an aggregation that matches ~15% of the rows
  • Inverted: 300 k doc IDs spread over every page → read the whole amount column
  • The inverted index answers the filter: the country column is never read
  • Per file: 2.1 M rows × 8 B ≈ 17 MB raw, ~10 MB compressed; 12 pages is schematic
  • Whole table: 10 TB ≈ 20 k files → ~200 GB and ~6 B rows read
  • Star-tree: split order (country, user), SUM(amount) pre-aggregated per node
  • Path: root → ES → * (any user) → 1 record per segment; pinned, so 0 bytes from S3
  • Star-tree is an Apache Pinot (OSS) index; External Tables can use it
  • Illustrative numbers
