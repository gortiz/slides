Close the cold open: this is why the two unlabeled diagrams looked the same. Then say where the mapping breaks: Iceberg files carry no indexes, and the writer decides their size, not Pinot.

One file, one segment

  • Name = hash of the file path
  • Paths never change content
  • Segment holds no data
  • Its forward index is the Parquet file
murmur3_128(dataFilePath). Sound only because Iceberg never rewrites a committed file. The segment is metadata, indexes, and a pointer to the Parquet file. It lives on the table's S3 tier like any tiered-storage segment.

From catalog to query

  1. Controller reads the snapshot
  2. New file: footer only, tiny segment
  3. Server builds indexes, stores them on S3
  4. Snapshot published
  5. Broker pins it per query
The controller never reads data, only footers. The server builds every index at load by reading the indexed columns once, then uploads the segment (metadata + indexes, no data) to the table's S3 tier. Later loads reuse it while segment and index config are unchanged. Say the price: one read per indexed column per segment, and index storage (270 GB on 770 GB in the published benchmark).

Reading without a copy

  • Indexes give exact doc IDs
  • Page index gives byte ranges
  • Ranged GETs, only those pages
  • 512 MB file, 0.5 MB read
The persisted page index is about 32 to 36 bytes per page, memory-mapped, and embeds the footer. Built once per segment because writers do not reliably write Parquet's own page index.

Where the rows go

  • 12.2 billion rows
  • Segment pruning: 3.9 billion
  • Indexes: 80 million
  • 99.3% never read
Q2 of the published StarTree benchmark (770 GB of Parquet on S3). Segment pruning plays the role of Iceberg's manifest pruning; the indexes do what min/max cannot. For the map-column query the funnel ends at 25 rows.

Two questions decide everything

  • Did you create indexes?
  • Can the query use them?
  • Either "no": a scan, like everyone
  • Both "yes": read only what you need
External Tables are one feature. Indexes are optional. Without them, or for a query that cannot use them, Pinot reads Parquet like any other engine.

You cannot beat physics

  • Need every value? Move every byte
  • From S3: pay per query
  • Local copy: pay storage and sync
  • Indexes change how many bytes
The honest message. Pinot covers both ends, and External Tables give it the middle. Ask before the talk whether one table can be native realtime for recent data and external for history.

Never mix two snapshots

  • Compaction: 10 files become 1
  • Mix before and after?
  • Rows twice, or not at all
  • Broker pins one snapshot per query
Each snapshot is a final.parquet in Pinot's deep store; the broker routes only to its segments and fails closed if it cannot pin one. Segment groups keep this workable with millions of files: content-addressed names make retries idempotent and reuse unchanged groups across snapshots.

What to keep local

  • Cold, nothing local: ~0.5 s
  • Pinned indexes: needed for QPS
  • Page cache: helps scans
  • …and can hurt selective queries
From the published benchmark: Q2 is 515 ms cold, 483 ms with index pinning, 1,211 ms with pinning plus the disk page cache. For index-driven queries, caching data pages adds overhead. The older throughput chart (image-30) shows the other side: without anything local, concurrent throughput collapses (filters 80 QPS, aggregations 20). Single query latency and sustained QPS are different questions.

Write Iceberg for its readers

  • Sort by the filter key
  • Sane file and row-group sizes
  • v3 deletion vectors
  • Compact on a schedule
Advice that helps every engine, not only Pinot. Comcast cut 35 to 40 percent of scanned data just by partitioning and sorting by device ID. Pinot applies deletion vectors only; older delete files are not applied, so prefer v3 DVs.

Configure Pinot for your queries

  • Index what you filter on
  • Star-tree for dashboards
  • Size the cache
  • Same region as the bucket
Every index costs one read of its column when the segment is first processed, plus storage on the S3 tier. Ranged S3 reads are region-strict.

Pick the mode

  • Selective, high QPS: External Tables + indexes
  • Full scans, high QPS: local copy
  • Ad-hoc exploration: a scan engine
  • Sub-second freshness: realtime
Say plainly where Pinot is not the answer: ad-hoc exploration over everything is Trino's job. Pinot's strength is covering the modes that a product feature needs. Counter-example worth citing: Comcast serves a 107 QPS internal API (p95 under 800 ms) straight from S3 Tables with Lambda, no indexes, because the data is partitioned and sorted by the lookup key. Clustered data makes the scan mode viable.
