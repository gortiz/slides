CHAPTER 2 Pinot Analytics as a product feature

Why Pinot exists

  • Analytics for every user: thousands of QPS, tens of ms
  • A warehouse serves analysts; Pinot serves the product

The moving parts

  • Controller: metadata, assignment
  • Broker: plans, routes, merges
  • Server: stores, executes
  • Minion: background jobs
  • ZooKeeper + deep store
  • Only what the next diagrams need
  • Unlike Iceberg: running servers
  • Clients send SQL to the broker

Tables all the way down

  • Table
  • Partitions
  • Segments: immutable, columnar
  • Metadata + indexes per column
  • Segment: self-contained (forward, dictionary, indexes, metadata)
  • Metadata per column: min, max, cardinality: the broker prunes on it
  • Indexes are per-column plugins: that is what makes External Tables possible

Offline ingestion

  1. Job builds a segment
  2. Upload to deep store
  3. Controller registers it
  4. Servers download and serve
  • Build an immutable file, store it, flip the metadata
  • = an Iceberg commit, years earlier

Realtime ingestion

  1. Servers consume a Kafka partition
  2. Rows are queryable at once
  3. Segment fills up
  4. One replica commits it
  5. It becomes immutable
  • Happy path only
  • Realtime data also ends as immutable segments

A SQL query, end to end

  1. Broker prunes segments
  2. Leaf stage: servers scan with indexes
  3. Intermediate stages: shuffle, join, aggregate
  4. Broker returns the result
  • Broker prunes on metadata before any server reads a byte
  • Leaf stages: servers that hold the segments, with indexes
  • Intermediate stages: shuffle, join, aggregate

Reading one Pinot segment

  • Same query as the hard case, now on one Pinot segment
  • Metadata is in memory: the broker prunes by partition, no I/O
  • Dictionary: the same trick as Parquet
  • Inverted index: exact doc IDs, 0 rows scanned to filter
  • Forward index: 3 rows read (numEntriesScannedPostFilter = 3)
  • Min/max says which files might; an index says which rows
  • Illustrative numbers

Segments live in the deep store

  • Every segment is in the deep store
  • Servers keep a local copy
  • Server dies? Download again
  • Rebalance: move assignments
  • Every segment is in S3, GCS or HDFS
  • The server copy is a cache: reassign and rebalance = download
  • Ask: why keep the local copy at all?

Tiered storage

  • StarTree only: the segment stays in S3, one copy, uncompressed
  • Not lazy loading: never downloads the whole segment
  • Local: metadata, buffer offsets, pinned indexes (preload.index.keys)
  • Raw forward index: 1,000 docs per chunk = 8 KB for a LONG; 3 GETs ≈ 24 KB
  • Less disk, a few ms more per GET
  • Bridge: an External Table segment is a tiered segment whose forward index is a Parquet file
