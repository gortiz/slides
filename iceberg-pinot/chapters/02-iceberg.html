Warehouse, lake, lakehouse

  • Layers, not four separate things
  • Lake = where the files are; Hive / Iceberg = which files make a table
  • Hive fails: listing, no atomic commits, users know the partitions, schema by position
  • Lakehouse = lake + table format (marketing name)
  • Two minutes max

A format, not an engine

  • No Iceberg server
  • No coordinator
  • A spec plus libraries
  • Every engine embeds them
  • Many writers, many readers
  • No server, no coordinator: writers only swap the catalog pointer
  • Pinot is servers, Iceberg is files

Parquet 101

  • Row group: horizontal slice
  • Column chunk: one column, contiguous
  • Page: smallest readable unit
  • Footer: offsets, stats, schema
  • No page offsets in the footer
  • Row group: ~128 MB or 100k rows
  • Page: ~1 MB or 20k rows
  • Dictionary: ~1 MB

Reading one Parquet file

  • Footer first: ~16 KB tells where everything is
  • File sorted by ts: min/max skips 7 of 8 row groups
  • Columnar: only 3 of 5 columns needed
  • Read user first (~4 MB): dictionary + ids; value missing = skip the row group
  • Then ts and amount: ~20 MB of 512 MB

Building a table, bottom-up

  • Catalog: one pointer per table, the only mutable thing
  • metadata.json: schemas (field IDs), partition specs, list of snapshots
  • Manifest list: one row per manifest + partition ranges: skip manifests
  • Manifest: one row per file + partition + column min/max: skip files
  • Q: does the catalog store the schema? No, metadata.json (Glue keeps a copy)
  • Q: many commits? expire_snapshots, rewrite_manifests, compaction

A commit

  1. Write new data files
  2. Write new manifests
  3. Write new metadata.json
  4. Swap the catalog pointer
  5. Lost the race? Retry
  • Optimistic: no locks, no coordinator
  • "If possible": re-validate; appends retry, conflicting deletes or compactions abort
  • Old manifests reused: a commit writes only what changed
  • v4 keeps snap-3: time travel (FOR VERSION AS OF 3)

Never mix two snapshots

  • Compaction: 10 files become 1
  • Mix before and after?
  • Rows twice, or not at all
  • Every read pins one snapshot
  • Compaction = a commit that swaps 10 files for 1
  • Mixing two snapshots double-counts rows
  • Every reader pins one snapshot; Pinot's broker too

Time travel

  • Old trees stay reachable
  • FOR VERSION AS OF
  • Branches and tags
  • Until snapshots expire
  • 30 seconds: free from the tree
  • expire_snapshots bounds it

Deletes: who pays?

  • Copy-on-write: writer rewrites files
  • Merge-on-read: writer adds a delete file
  • Reader merges at scan time
  • Compaction folds them back
  • Copy-on-write: the writer rewrites files
  • Merge-on-read: readers merge delete files
  • Format version caps what writers use; the engine picks per operation

Merge-on-read, three ways

  • Position deletes v2: file + row
  • Equality deletes v2: "where id = 42"
  • Deletion vectors v3: one bitmap per file

Puffin: a blob file format from the Iceberg spec. It stores DVs and statistics.

  • Optional
  • Equality deletes: cheap for Flink, expensive for readers
  • Deletion vectors: one bitmap per file, cheapest
  • Formats can mix in one table (v2 upgraded to v3)

Hidden partitioning

  • Partition by a transform
  • day(ts), bucket(16, user)
  • Users filter on ts
  • Change the spec, keep old files
  • Optional
  • User filters on ts; the engine derives the partition
  • Hive: users had to filter on dt

Pruning: ideal case

  • Partition: assume day(ts) and bucket(16, user)
  • Inside the day: files in time order
  • Query: the last hour
  • One file overlaps: skip the rest
  • Say: PARTITIONED BY day(ts), bucket(16, user)
  • Day partition keeps today
  • Files in time order: one overlaps the last hour
  • Min/max rewards clustering

Pruning: ideal case

  • Manifest list: partitions
  • Manifests: file min/max
  • Columnar: needed columns only
  • Footer: skip row groups
  • Page index: skip pages
  • 10 TB → 27 GB (day) → 2.3 GB (file min/max) → 190 MB
  • Illustrative numbers

Pruning: hard case

  • Partition: 1 bucket of 16
  • Inside the bucket: user spread out
  • Every range contains it
  • Min/max skips nothing
  • Partition: 1 bucket of 16
  • Files in time order, not user order: every range contains 'bob'
  • Min/max: "which files might" = all of them

Pruning: hard case

  • Filter on user only
  • Bucket: 1/16 of the data
  • File min/max: no help
  • Columnar still helps
  • ~29 GB for a few rows
  • No time filter: only the bucket helps
  • 10 TB → 625 GB (bucket) → 625 GB (min/max) → ~29 GB
  • ~29 GB for a few KB of rows: fine for an analyst, not for an app
  • Illustrative numbers
