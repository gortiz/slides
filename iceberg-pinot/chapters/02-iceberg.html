CHAPTER 1 Iceberg A table format, built bottom-up

Warehouse, lake, lakehouse

  • Warehouse: ETL into closed storage
  • Lake: cheap files, schema on read
  • Hive: a table is a directory
  • Lakehouse: open files, real tables
Keep this to two minutes. The transition that matters is Hive to Iceberg. Hive's four failures: listing is the planner, no atomic commits, users must know the partitioning, schema by position. Iceberg fixes each one.

A format, not an engine

  • No Iceberg server
  • A spec plus libraries
  • Every engine embeds them
  • Many writers, many readers
This is the mental model for everything that follows. Iceberg needs engines to be useful. Pinot is one of them. Contrast to remember for chapter 2: Pinot is servers, Iceberg is files.

Parquet 101

  • Row group: horizontal slice
  • Column chunk: one column, contiguous
  • Page: smallest readable unit
  • Footer: offsets, stats, schema
  • No page offsets in the footer
The last bullet sets up chapter 3: to find one page you must walk the page headers in the chunk, unless the writer added the optional page index. Writers disagree on that, so you cannot rely on it.

Building a table, bottom-up

Start from what people know: Parquet files. Each layer answers a question about the layer below. Manifests: which files, and their min/max per column. Manifest list: which manifests, with partition ranges. metadata.json: schemas by field ID, partition specs, the snapshot list. The catalog holds one pointer, and it is the only mutable thing.

A commit

  1. Write new data files
  2. Write new manifests
  3. Write new metadata.json
  4. Swap the catalog pointer
  5. Lost the race? Retry
Optimistic concurrency: no locks, no coordinator. Readers that started earlier keep reading the old tree. Old manifests are shared between snapshots, so a commit writes only what changed.

Iceberg is a B-tree of files where only the root pointer is mutable.

Pause here. Engineers who know databases get the whole format from this sentence.

Time travel

  • Old trees stay reachable
  • FOR VERSION AS OF
  • Branches and tags
  • Until snapshots expire
Thirty seconds. It falls out of the tree for free; maintenance (expire snapshots) bounds it.

Hidden partitioning

  • Partition by a transform
  • day(ts), bucket(16, user_id)
  • Users filter on ts
  • Change the spec, keep old files
Compare with Hive: there the user had to know and filter on the dt folder.

Deletes: who pays?

  • Copy-on-write: writer rewrites files
  • Merge-on-read: writer adds a delete file
  • Reader merges at scan time
  • Compaction folds them back
Both strategies exist in every version that supports deletes. The table's format-version caps what writers may produce; the engine chooses per operation (Spark: write.delete.mode and friends).

Merge-on-read, three ways

  • Position deletes v2: file + row
  • Equality deletes v2: "where id = 42"
  • Deletion vectors v3: one bitmap per file

Puffin: a blob file format from the Iceberg spec. It stores DVs and statistics.

Equality deletes are cheap for streaming writers such as Flink and expensive for every reader. DVs are the cheapest to apply: one bitmap AND. Formats can mix inside one table, for example a v2 table upgraded to v3 with old position-delete files still around.

How a scan engine prunes

  • Manifest list: partitions
  • Manifests: file min/max
  • Footer: row group stats
  • Page index: page min/max
Introduce the byte counter here. It stays in the corner for the rest of the talk and shows requests and bytes for the same query under each approach.

Where min/max gives up

  • Table sorted by ts
  • Filter on user_id
  • Every range contains it
  • Nothing prunes: full scan
Min/max answers "which files might contain it". On unclustered columns the answer is "all of them". You need something that answers "which rows".

Even Spotify adds an index

  • Point queries on the lake
  • External index: key → file, rows
  • Ranged reads, only needed bytes
  • The lake wants indexes

engineering.atspotify.com · "Indexing the data lake for online point queries" (2026)

Spotify built Random Access Parquet: an external index over Parquet in GCS, cached metadata to turn rows into page locations, and parallel ranged reads. Independent validation of the idea in chapter 3, from a team with no stake in Pinot. Note it works on Parquet, without Iceberg.
