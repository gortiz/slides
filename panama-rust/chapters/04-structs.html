Returning multiple values

  • find() should return:
    • did it match?
    • start offset?
    • end offset?
  • C ABI: one return value → needs a struct
  • JNI — Rust can construct Java objects
  • Panama — Rust has no JVM access
    • → return a Rust struct
  • want richer find: did it match? where? offsets?
  • one return value → struct
  • JNI (skipped — code in repo): Rust does 3 JVM upcalls (find_class + get_method_id + new_object) to build the Java object
  • Panama (what we'll build): no JVM access → return a plain Rust struct; Panama maps it to off-heap memory

Returning a struct: JNI

record JavaMatchResult(
    boolean found,
    int start,
    int end) {}

private native JavaMatchResult findNative(
    long ptr,
    String haystack);

public JavaMatchResult find(String haystack) {
    return findNative(ptr, haystack);
}
#[no_mangle]
pub extern "system" fn Java_..._findNative(
    mut env: JNIEnv, _class: JClass,
    regex_ptr: jlong, haystack: JString,
) -> jobject {
    let regex: Regex = ...;
    let hay: String = ...;
    let cls  = env
        .find_class("org/example/JavaMatchResult")
        .unwrap();
    let ctor = env
        .get_method_id(cls, "", "(ZII)V")
        .unwrap();
    match regex.find(&hay) {
        None => env.new_object(cls, ctor,
            &[false.into(), 0.into(), 0.into()]
        ).unwrap().into_raw(),
        Some(m) => env.new_object(cls, ctor,
            &[true.into(), m.start().into(), m.end().into()]
        ).unwrap().into_raw(),
    }
}
  • Java side reads clean: a record + a native method — cost is hidden
  • return type jobject = opaque ref, no generics, no type info
  • find_class(string) + get_method_id(name + "(ZII)V"): 2 JNI upcalls per call
  • cacheable but tricky — find_class returns a local ref → must promote to GlobalRef
  • new_object = upcall #3
  • rename the Java class or constructor → silently breaks at runtime

Finding a match

  • 🔑 the arena owns the return slot — Panama allocates into it on every invoke
  • Rust returns by value (idiomatic); the C ABI moves the bytes into the arena
  • VarHandle reads pull fields out of that same off-heap memory — no JNI upcalls
  • memory frees when the arena closes

  • 12 bytes: found at +0, 3 bytes of padding, start at +4, end at +8 (an i32 starts at a multiple of 4)

Finding a match — Java

static final StructLayout MATCH_RESULT = MemoryLayout.structLayout(
  JAVA_BOOLEAN.withName("found"),
  MemoryLayout.paddingLayout(3),   // 3B pad → start/end align to 4
  JAVA_INT.withName("start"),
  JAVA_INT.withName("end"));
static final VarHandle FOUND =
  MATCH_RESULT.varHandle(groupElement("found"));
static final VarHandle START =
  MATCH_RESULT.varHandle(groupElement("start"));

  MATCH_RESULT.varHandle(groupElement("end"));

static final MethodHandle FIND =
  Linker.nativeLinker().downcallHandle(...)

public JavaMatchResult find(String haystack) {

    if (!(boolean) FOUND.get(out, 0L)) {

    } else {
      // Do something with (int) START.get(out, 0L)
      // and (int) END.get(out, 0L)
    }

}
  • Java only gets a MemorySegment: an address and 12 bytes, no names, no types
  • the layout must mirror the Rust struct EXACTLY — incl. paddingLayout(3)
  • each VarHandle = offset + type from the layout: FOUND +0, START +4, END +8; typed, bounds-checked
  • skip the padding and START reads +1…+4 = 00 00 00 00 → 0 (looks right by luck!), END reads +5…+8 = 00 00 00 05 → 83,886,080
  • 🔑 return is a group layout → FIND.invoke gets an extra leading SegmentAllocator param (the arena)
  • last step: FOUND.get(out, 0L) reads byte +0 → true
  • nobody writes this by hand → next: cbindgen + jextract generate it
