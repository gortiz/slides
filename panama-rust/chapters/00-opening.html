Why call native code?

  • Ecosystem access — reuse Rust/C/C++ libraries that already exist.
    ML inference (ONNX), compression (zstd), databases. Don't rewrite them.
  • Ergonomics — some problems are more natural with direct memory control.
    SIMD intrinsics, memory-mapped structures, zero-copy I/O.
  • Performance — bypass JIT/GC limits…
    Be careful — the JVM is surprisingly good. Native isn't a magic speed button.
  • 3 reasons: ecosystem · ergonomics · performance
  • ecosystem = the most common one (ONNX, zstd, …)
  • perf — be careful. JIT is great. Native isn't a magic button

The two bridges

JNI — in the JDK since Java 1.1  ·  Panama FFM — finalized in Java 22

  • JNI: shipped in JDK since 1.1
  • Panama FFM: finalized in Java 22
  • both bridges go both directions (downcall + upcall)

Same call, two philosophies

JNI — object-centric

[lib]
crate-type = ["cdylib"] 

[dependencies]
jni = "0.21"
  • Rust receives Java objects
  • JVM may pin objects
  • Rust crate coupled to the JVM

Panama — mem-centric

[lib]
crate-type = ["cdylib"]
  • Rust receives raw memory
  • No GC interaction — data lives off-heap
  • Same standard C ABI
    • Already used by Python, Go, Node…
  • JNI: needs the jni crate — Rust now depends on JVM types and calling conventions
  • Panama: just cdylib. Rust doesn't know Java exists
  • JNI = object-centric: lets native pretend it has Java objects → hidden cost
  • Panama = memory-centric: no objects cross the boundary — JVM has nothing to do
  • bonus: Rust exposes the same C ABI Python / Go / Node already use
