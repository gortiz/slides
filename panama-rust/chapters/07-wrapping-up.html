  • ✓ Strings — isMatch(pattern, haystack)

When should you reach for native?

ReasonWorth it?Notes

  • ecosystem ✓ — best reason, library already exists
  • ergonomics ✓ — SIMD, mmap, deterministic latency (real JVM blind spots)
  • performance ⚠ — be skeptical. Bridge has fixed cost; String calls always pay UTF-16↔UTF-8
  • (if time) regex is fast because of algorithm (Thompson NFA), not Rust — picked for the API surface, not the speed

Performance tips

  • Each call is expensive.
    • JNI slower than Panama
  • One broad > many narrow.
  • Shared memory > copies.
  • Do not use Java Strings.
  • Use async-profiler — not JFR.
  • each call costs in BOTH bridges (state transition, safepoints, GC); JNI adds pinning + ref-table mgmt
  • one broad call > many narrow — batch on the native side; shared memory > copies
  • avoid Java Strings — work with UTF-8 byte[]
  • profile with async-profiler, NOT JFR (JFR stops at the boundary)

⚠️ One last critical part

  • pause beat — one last thing you cannot get wrong

⚠ A panic will kill the JVM

let regex = Regex::new(&pattern).expect("Invalid regex");
//                               ^^^^^^^ panic on invalid input!
A panic across extern "C" is undefined behavior.
No stack trace. No exception. The JVM just dies.
  • we used .unwrap() / .expect() everywhere
  • panic across extern "C" = UB → JVM dies
  • no stack trace, no exception, just process gone
  • this IS the production footgun

Catch panics at the boundary

// Rust: catch the panic, signal failure with a null pointer
pub extern "C" fn create(
    pattern_ptr: *const u8, pattern_len: usize,
) -> *mut RegexHandle {
    let result = std::panic::catch_unwind(|| {
        let pattern = bytes_to_str(pattern_ptr, pattern_len)?;
        Ok(Regex::new(pattern)?)
    });
    match result {
        Ok(Ok(regex)) => Box::into_raw(Box::new(RegexHandle { regex })),
        _ => std::ptr::null_mut(), // in case of error
    }
}
Alternative to returning null?   Why not throw an exception?
  • catch_unwind wraps the body — panic caught before crossing the boundary
  • signal failure with a sentinel: null pointer
  • 🎤 ASK AUDIENCE: "why not throw an exception?"
  • answer: Panama has no env.throw. No JNIEnv = no way to raise a Java exception from Rust. Java wrapper does it: sees null → throws

Same islands, a better bridge

JNI hands native code the JVM  ·  Panama hands it plain memory

  • bookend — we opened on these two bridges; we close on them
  • the philosophical shift: JNI is object-centric — native pretends to hold Java objects → pinning, string lookups, hidden copies, and a Rust crate coupled to the JVM
  • Panama is memory-centric — nothing crosses the boundary but pointers and bytes
  • what that buys: no JVM types in your Rust · the same C ABI Python/Go/Node already use · costs are explicit & JIT-visible · deterministic off-heap lifetimes via Arena · cbindgen + jextract generate the boilerplate
  • the takeaway: with Panama, calling native code is a library decision, not a scary one
