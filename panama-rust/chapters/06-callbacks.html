Can we call Java from Rust?

  • flip the arrow: everything so far was Java→Rust (downcalls); now Rust→Java (upcalls / callbacks)

Callback/upcalls

// Rust calls back into this interface
interface MatchVisitor {
    // true = continue, false = stop early
    boolean onMatch(int start, int end);
}

// Usage — pass a lambda
regex.findAll(haystack, (start, end) -> {
    System.out.println(
        "match at " + start + ".." + end);
    return true;  // keep going
});
  • so far: Java→Rust. Now reverse: Rust→Java (upcall)
  • use case: findAll over a big text — don't buffer all matches in native memory; we want one callback per match, with early-stop
  • left = the Java contract: a one-method interface MatchVisitor, callable as a lambda; true → keep going, false → stop
  • right = the streaming sequence. Clean Java — the bridge code is what gets ugly

Callbacks: JNI

#[no_mangle]
pub extern "system" fn Java_..._forEachMatch(
    mut env: JNIEnv, _class: JClass,
    ptr: jlong, haystack: JString,
    visitor: JObject,   // the MatchVisitor instance
) {
    let regex = unsafe { &*(ptr as *const Regex) };
    let haystack_str: String = env.get_string(&haystack).unwrap().into();
    for m in regex.find_iter(&haystack_str[..]) {
        let keep_going = env.call_method(
            &visitor,          // Java object
            "onMatch",         // method name (string!)
            "(II)Z",           // JNI type signature (string!)
            &[JValue::from(m.start() as jint),
              JValue::from(m.end() as jint)]
        ).expect("onMatch call failed")
         .z().expect("must return boolean");
        if !keep_going { break; }
    }
}
  • visitor arrives as JObject — opaque ref, no interface type
  • env.call_method: name AND descriptor are STRING LITERALS — typo crashes at runtime
  • "(II)Z" = (int, int) → bool — JVM type descriptor language
  • 🔑 this upcall fires on EVERY iteration. Thousands of matches → thousands of crossings

Callbacks — Java

// plain Java method — the callback target
boolean onMatch(int start, int end) { … }

// one-time: lift it into a MethodHandle
static final MethodHandle BRIDGE =
    MethodHandles.lookup().findVirtual(
        PanamaRsRegex.class, "onMatch",
        MethodType.methodType(
            boolean.class, int.class, int.class));

// one-time: downcall (last param = fn pointer)
static final MethodHandle FOR_EACH_MATCH =
  LINKER.downcallHandle(
    LIB.find("for_each_match").orElseThrow(),
    FunctionDescriptor.ofVoid(
        ADDRESS, ADDRESS, JAVA_LONG, ADDRESS));

public void forEachMatch(String haystack) {
  try (Arena arena = Arena.ofConfined()) {
    // a REAL native function pointer
    MemorySegment stub = LINKER.upcallStub(
        BRIDGE.bindTo(this),
        FunctionDescriptor.of(
            JAVA_BOOLEAN, JAVA_INT, JAVA_INT),
        arena);
    MemorySegment cHay = arena.allocateFrom(
        JAVA_BYTE, haystack.getBytes(UTF_8));
    FOR_EACH_MATCH.invoke(
        handle, cHay, cHay.byteSize(), stub);
  }
}
  • left: onMatch is a plain Java method — nothing special. findVirtual lifts it into a MethodHandle once (no per-call FindClass). Downcall handle's last ADDRESS = the fn-pointer slot
  • right: upcallStub wraps the MethodHandle (bound to this with bindTo, since onMatch is an instance method) into a REAL native function pointer Rust can call directly
  • FunctionDescriptor must MATCH the Rust MatchCallback exactly; stub lifetime = arena lifetime
  • 🔑 the contrast: JNI = N upcalls + N string lookups. Panama = 1 stub + N raw fn-ptr calls — measurable over a big corpus
  • 🔧 stamp: in production you don't hand-write this binding boilerplate — jextract generates the lookups, downcall handles, descriptors & layouts (the upcallStub wiring for your own callback you still write)
